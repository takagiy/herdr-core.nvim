# 主要な利用経路は実際の hc を通す E2E で検証し、通常テストとは分けて実行する

## 状況

通常テストは実際の Neovim の UI を使うが、hc の通信はテスト用の応答に置き換えている。実際の attach の入出力、配置の復元、複数 Neovim 間の同期までは保証できない。一方、普段の開発で毎回外部プロセスを起動するテストを走らせると、待ち時間と環境への依存が増える。

## 決定

- 通常テストと E2E を分けて実行する。通常テストは hc なしで動く。
- E2E は、Neovim、プラグイン、hc、起動したプログラムをすべて実物で通す。通信や内部モジュールを mock に置き換えない。
- エージェントの代わりに、認証の要らない dummy agent を使う。Claude や Codex の実起動は必須にしない。
- E2E は Linux で実行する。Windows のヘッドレスの Neovim の中では `hc attach` が終了コード 2 で終わるため、Windows では実行しない（手で起動した Neovim では動く）。
- E2E が使う hc の版はリポジトリで固定し、新しい版は Renovate の PR で E2E を通してから上げる。

## 結果

得たもの:

- 日常のテストを軽量に保ち、実際のプロセスを通る主要経路を別に検証できる。
- どの hc の版で通ったかが履歴に残る。

失ったもの:

- E2E は外部プロセスとタイミングに依存し、準備と失敗調査に時間がかかる。
- Windows と macOS の挙動は、自動では確かめない。ローカルで E2E を動かすには Docker が要る。

## 採らなかった案

- 通常テストに E2E を混ぜる。普段の開発にも hc と外部プロセスの準備が必要になる。
- Claude・Codex を必須にする。認証・料金・応答待ちが必要になり、再現しやすい状態変化を作りにくい。
- 毎回、実行時の最新の hc を使う。どの版で通ったかがリポジトリに残らない。
- Dependabot で版を上げる。hc は GitHub Releases がなく、Dependabot が扱える依存の種類に当たらない。
- Windows のヘッドレスの Neovim でも attach が通るよう、製品のコードで `hc attach` を `cmd.exe` 経由で起動する。テストのためだけに製品のコードが増え、試した範囲では通らなかった。
