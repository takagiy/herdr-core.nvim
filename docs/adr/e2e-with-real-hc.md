# 主要な利用経路は実際の hc を通す E2E で検証し、通常テストとは分けて実行する

## 状況

通常テストは実際の Neovim の UI を使うが、hc の通信は多くをテスト用の応答に置き換えている。実際の attach の入出力、配置の復元、複数 Neovim 間の同期までは保証できない。一方、普段の開発で毎回外部プロセスを起動するテストを走らせると、待ち時間と環境への依存が増える。

この決定は [mini.test を使う決定](tests-with-mini-test.md) を補足し、E2E の CI 対象は Linux とする。具体的な技術とテスト用プログラムは [E2E の技術選定](e2e-toolchain.md) に従う。

## 決定

### 実行を分ける

- `mise run test` は軽量な通常テスト、`mise run test-e2e` は E2E を実行する。既存の実際の hc を使うテストも E2E に移し、通常テストは hc なしで実行できるようにする。
- E2E も mini.test を使う。Neovim → プラグイン → hc → 起動したプログラムをすべて実物で通し、通信や内部モジュールを mock に置き換えない。
- 主要な操作はキー入力とマウス操作で行う。初期設定と結果の確認には Neovim の API と hc の正式な API を使ってよい。合否は表示内容、フォーカス、配置、保存結果で判定し、画面の完全一致は求めない。
- 必要な Neovim、hc、Node.js がなければスキップせず失敗させる。
- E2E は Linux で実行する。CI とローカルの Docker（`mise run test-e2e-linux`）は、同じスクリプト `scripts/e2e-linux.sh` を使う。Windows のヘッドレスの Neovim の中では `hc attach` が終了コード 2 で終わるため、Windows では実行しない。手で起動した Neovim では、Windows でも attach が動く。

### テスト用のプログラムを共通にする

hc に対応した認証不要の dummy agent が使えるかを先に調べ、使えれば最初から採用する。これは hc 上で動く実際のプロセスであり、通信を置き換える mock ではない。Claude・Codex の実起動や API キーは必須にしない。

同じことを解決する仕組みを複数作らない。dummy agent で入力・出力と状態変化を検証できれば、その目的の別プログラムや別の状態生成手段は作らない。シェル自体を起動する利用経路は実際のシェルで確認する。

dummy agent で必要な状態変化を扱えなければ、hc の正式な API で状態を変更する方法を確認する。既存の手段で足りない場合に限り、必要最小限のテスト用プログラムを用意する。採用する仕組みは実装前に確認する。

### 主要な利用経路を通す

1. 新規起動、入力と出力、window を閉じた後の再接続。window を閉じてもプログラムは動き続ける。
2. サイドバーから開く、名前変更、ピン留め、折りたたみ。
3. 起動ディレクトリの repo root によるスペース分類。
4. tab・分割配置の保存と Neovim 再起動後の復元。
5. 2つの Neovim 間での名前・ピン・配置の同期。

通知は実際の状態変化から OS 通知コマンドの実行成功までを自動検証する。コマンドの成功は画面への表示を保証しないため、表示は手動確認とする。リモート接続は従来どおり best effort とし、E2E 対象に含めない。

### 普段の環境から分離する

テスト専用の hc 環境、作業ディレクトリ、Neovim を使い、普段のセッションや保存済みの配置に触れない。分離方法は hc の対応を確認して決める。

失敗時も Neovim の画面・メッセージと hc の状態・ログを保存してから、テスト専用のプロセスを終了する。保存する記録に普段のセッションを含めない。

### hc の版を固定し、新しい版は Renovate の PR で確かめる

- E2E が使う hc の版は `mise.toml` の `HC_VERSION` に書き、リポジトリで固定する。`main` に入っている版が、E2E が通った版になる。
- Renovate が `releases.herdr.dev/core/latest.json` を見て、新しい版が出たら `HC_VERSION` を上げる PR を作る。E2E は PR でも実行し、その PR で新しい版を確かめる。Renovate の PR では、E2E が動く土台（Neovim、Node.js、hc）を更新するときだけ実行し、GitHub Actions などの更新では実行しない。
- Linux で毎日、日本時間の午前6時を目安にも実行する。手動起動では、別の版を指定して実行できる（以前に通った版との比較など）。
- 任意項目として、操作内容と時刻、操作の区切りごとの画面を trace として残し、失敗時に CI から取得できるようにする。動画や再生ビューアは初期実装に含めない。

## 結果

得たもの:

- 日常のテストを軽量に保ち、実際のプロセスを通る主要経路を別に検証できる。
- 認証情報なしで実行でき、新しい hc の版を PR ごとに確かめられる。どの版で通ったかが履歴に残り、前の版との比較も、その版を指定して実行し直すだけで済む。
- テスト用のプログラムを共通にし、同じ状態を作る仕組みの重複を避けられる。

失ったもの:

- E2E は外部プロセス、通知機構、実行時のタイミングに依存し、通常テストより準備と失敗調査に時間がかかる。
- 新しい hc の版を試すのは、Renovate が PR を作ってからになる。Renovate の GitHub App をリポジトリに入れる必要がある。
- Windows・macOS の挙動は自動では確かめない。Windows の attach は、手で起動した Neovim で確かめる。OS 通知の表示とリモート接続も自動検証の範囲外に残る。
- ローカルで E2E を動かすには Docker が要る。

## 採らなかった案

- 通常テストに E2E を混ぜる。普段の開発にも hc と外部プロセスの準備が必要になる。
- Claude・Codex を必須にする。認証・料金・応答待ちが必要になり、再現しやすい状態変化を作りにくい。
- dummy agent と別の仕組みで同じ入出力や状態変化を作る。維持する仕組みが増えるため、使えるものを最初から共通にする。
- 毎回、実行時の latest を使う。どの版で通ったかがリポジトリに残らず、版を記録して比べる仕組みを別に作る必要がある。
- Dependabot で版を上げる。hc は GitHub Releases がなく、Dependabot が扱える依存の種類に当たらない。
- 画面の完全一致や OS 通知の表示検出を必須にする。主要な振る舞いの検証に対して、環境差への対応が増える。
- Windows のヘッドレスの Neovim でも attach が通るように、製品のコードで `hc attach` を `cmd.exe` 経由で起動し、コンソールにつなぎ直す。テストのためだけに製品のコードへ層が増え、試した範囲では通らなかった。attach の可否はシェルや端末の種類によるとみられ、調べる時間に見合わない。
