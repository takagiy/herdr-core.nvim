# サイドバーの中身をリソースが通知する Section と Item の木にし、ターミナルの一覧もその 1 つにする

## 状況

[サイドバー](sidebar.md)に出せるのは、スペースごとのターミナルと、その下の子ターミナルだけだった。タスクのように、ターミナルではない情報も同じ場所に並べたい。

利用者が描画まで書くと、状態の記号、色、行の形が定義ごとに変わる。見た目は、どの項目でも揃えたい。

並べたいデータの元は、ファイル、外部のプロセス、タイマーのように、あとから変わるものが多い。hc のターミナルは、adapter が一覧を取り、core が保持し、操作は core の effect を adapter と ui が実行している（[レイヤーの決定](module-layers.md)）。利用者のデータも同じ流れに乗せたい。

## 決定

### リソース

- `setup` の `resources` に、リソースの定義を並べる。定義は `name`、`parent`、`monitor`、`actions`、`keys` を持つ。`name` と `monitor` は必須。既定は `{ resources.terminals() }`。
- リソースは、Section と Item のリストを通知する。どちらも `require("herdr-core.resources")` のコンストラクタで作る。
  - `Section { id, name, notification_count, items, props }`
  - `Item { id, name, detail, status, notification_count, is_highlighted, items, props }`
- 表示に使うのは、上の決まったフィールドだけ。action に渡したい値は `props` に入れる。
- Section は見出しを描き、その下に `items` を並べる。トップレベルの Item は、見出しなしで並べる。Section の中に Section は置けない。
- `id` が同じ要素は、通知をまたいで同じものとして扱う。`id` のない要素は、位置で判定する。

### 親

- `parent` は、`"terminals[]"` のように、リソースの名前に `[]` を付けて書く。`[]` が 1 つなら通知のリストの要素、2 つならその `items` の要素を指す。3 つ以上も同じ。
- 親を持つリソースは、その段の要素ごとにモニターを 1 つ持つ。通知できるのは Item のリストだけ。通知した Item は、親の要素の `items` のあとに並ぶ。同じ親を持つリソースは、`resources` に書いた順に並ぶ。
- `parent` のないリソースは、`resources` に書いた順に、トップレベルに並ぶ。
- 存在しない名前を指す `parent`、循環する `parent`、重複した `name` は、`setup` でエラーにする。

### モニター

- `monitor()` は、インスタンス `{ arm, disarm }` を返す。親の要素ごとに 1 回呼ぶ。親のないリソースは、起動時に 1 回呼ぶ。
- `arm(ctx)` は、親が現れたときと、親の内容が変わるたびに呼ぶ。`ctx.parent` がいまの親、`ctx.notify(list)` が通知。張り替えるかどうかは、`arm` の中で決める。
- `ctx.notify` は、同じインスタンスには毎回同じ関数を渡す。どの callback から呼んでもよい。`disarm` のあとの通知は無視する。
- `disarm()` は、親が消えたときと、プラグインが止まるときに、1 回だけ呼ぶ。`arm` が失敗していても呼ぶ。省略はできない。
- モニターの失敗と、形の合わない通知は、内容ごとに 1 回だけ利用者に通知する。

### ターミナル

- ターミナルとスペースの一覧は、組み込みのリソース `terminals` にする。`resources.terminals({ keys })` が定義を返す。モニターは持たず、core が hc のデータから木を作る。
- スペースを Section にする。`id` と `props.space` は、スペースのルートのパス。
- ターミナルを Item にする。`id` と `props.address` はアドレス。`props.space` と `props.is_pinned` も持つ。子ターミナルは、Item の `items` に入れる。
- `is_highlighted` は、いまのタブページで前面にあるターミナルに付ける。前面のターミナルは、ui が event で core に伝える。
- リモートの machine は、別のリソースにする。それができるまで、リモートのターミナルはサイドバーに出さない。

### キーと action

- `actions` は、名前を付けた関数の表。`keys` は、キーから動作名か関数への対応。`use` は、Enter とクリックを表す。
- キーは Item にだけ効く。Section は action を受けない。効くのは、カーソル下の Item のリソースの `keys` だけ。`keys` のないリソースの Item には、`j`/`k` が止まらない。
- action は `ctx` を受け取る。`ctx.item` はその Item、`ctx.parent` は 1 つ上の要素。
- `terminals` の動作は、`open`、`rename`、`pin`、`unread`、`new_terminal`。`keys` を省略すると、Enter とクリックで `open`、`n`、`r`、`p`、`u` でほかの動作を使う。
- `setup` の `sidebar_keys` は廃止する。設定に残っていたら、`resources.terminals({ keys = ... })` に移すよう通知する。

### データの流れ

- **一覧**: モニターの通知を、`adapter/resources.lua` が event（`items_listed`）にする。core が state に保持する。
- **モニターの管理**: core が、どの親にモニターが要るかを state から求め、変わった分だけを effect（`sync_monitors`）で adapter に伝える。張っているインスタンスは adapter が持つ。
- **描画**: `view` は、state だけから行を作る。行は関数を持たない。
- **キー**: ui が行とキーを報告し、app が event（`key_pressed`）にする。core がキーを関数まで解決して effect（`run_action`）を返し、app が呼ぶ。`terminals` の action は、いままでの event（`terminal_chosen` など）を dispatch する。
- **定義**: 定義は、関数ごと core の state に置く。core は、その関数を呼ばない。

## 結果

得たもの:

- 利用者のデータが、hc のターミナルと同じ流れに乗る。adapter が取り、core が保持し、操作は effect で実行する。
- ファイルの監視、プロセス、タイマーのような非同期のデータの元を、そのまま書ける。張ったものの後始末は、プラグインが呼ぶ。
- core は利用者の関数を呼ばない。
- ターミナルの一覧と利用者の項目が、同じ語彙（Section、Item）で描かれる。子ターミナルも、利用者の項目も、ターミナルの下に同じ形で並ぶ。

失ったもの:

- リモートのターミナルが、サイドバーに出なくなる。machine の見出しと、その折りたたみもなくなる。
- `sidebar_keys` が使えなくなる。`activate` で行を押すキーを変えることも、できなくなる。
- スペースの見出しの上で `n` を押しても、ターミナルを起動しない。
- 親から計算するだけのリソースも、モニターの形（`monitor`、`arm`、空の `disarm`）で書く必要がある。
- 通知は次のメインループで反映する。親が現れてから項目が出るまでに、描画が 1 回挟まる。
- state と effect に関数が入る。そのままログに出しても、中身は読めない。
- `herdr.space` ラベルのないターミナルの上で `new_terminal` を使うと、そのターミナルの `cwd` をスペースにして起動する。これまでは、スペースを指定せずに起動していた。
- リソースの `keys` に書いたキーは、サイドバーのほかの行の上では何もしない。Neovim の標準の動作も出ない。

## 採らなかった案

- 記号の文字とハイライトグループを利用者が指定する。テーマから色を作る決まりの外に出て、見た目が揃わなくなる。
- 定義に、項目を返す関数（`items(ctx)`）を書く。非同期のデータの元では、利用者がキャッシュを持ち、再取得を頼む呼び出しが別に要る。モニターと併用すると、取得した内容と通知した内容が食い違う。
- モニターをリソースに 1 つだけ張る。取得する内容が親（`cwd` など）で変わるなら、監視する対象も親で変わる。
- インスタンスに `key` を持たせ、プラグインが比較して張り替える。張り替えの判断を `arm` に任せるほうが、プラグイン側が単純になり、モニターは張り替えずに設定だけを変えることもできる。
- `arm` が、止める関数を返す。`arm` を何度も呼ぶ形とは合わない。
- 子ターミナルを別のリソース（`subagents`）にする。子ターミナルはターミナルそのもので、同じデータを別の形で通知し直すことになる。
- core が、利用者の関数を直接呼ぶ。ターミナルと流れが変わり、core が外部の状態に依存する。
- machine を、Section を含む Section で表す。見出しの種類が増える。machine は別のリソースにする。
- `sidebar_keys` を残して、`terminals` の `keys` に変換する。同じことを書く方法が 2 つになる。
