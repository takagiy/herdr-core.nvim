# サイドバーの中身はリソースのモニターが通知し、ターミナルの一覧もリソースの 1 つにする

## 状況

[サイドバー](sidebar.md)に出せるのは、スペースごとのターミナルだけだった。タスクのように、ターミナルではない情報も同じ場所に、同じ見た目で並べたい。

並べたいデータの元は、ファイル、外部のプロセス、タイマーのように、あとから変わるものが多い。hc のターミナルは、adapter が一覧を取り、core が保持し、操作は core の effect を adapter と ui が実行している（[レイヤーの決定](module-layers.md)）。

## 決定

- リソースは、見出し（Section）と項目（Item）の木を通知する。表示はサイドバーが決まった形で描き、利用者は描画を書かない。
- リソースのデータは、ターミナルと同じ流れに乗せる。
  - モニターを adapter が張り、通知を event にする。core が state に保持する。
  - キーは event として core に届き、core が実行する関数を effect で返す。
  - 利用者の関数は state と effect に入るが、core は呼ばない。
- モニターは、親の要素（スペース、ターミナルなど）ごとに 1 つ作る。親が変わるたびに `arm(ctx)` を呼び、張り替えるかどうかはモニターが決める。親が消えたら `disarm()` を呼ぶ。
- ターミナルとスペースの一覧も、組み込みのリソースにする。キーは、リソースごとに書く。

## 結果

得たもの:

- ファイルの監視、プロセス、タイマーのような非同期のデータの元を、そのまま書ける。後始末はプラグインが呼ぶ。
- ターミナルと利用者の項目が、同じ見た目と同じ操作で並ぶ。

失ったもの:

- 他のマシンのターミナルは、machine のリソースができるまでサイドバーに出ない。
- サイドバー全体のキーの設定（`sidebar_keys`）がなくなる。
- 親から計算するだけのリソースも、モニターの形で書く必要がある。
- state と effect に関数が入る。そのままログに出しても、中身は読めない。

## 採らなかった案

- 記号の文字とハイライトグループを利用者が指定する。見た目が揃わなくなる。
- 定義に、項目を返す関数（`items(ctx)`）を書く。非同期のデータの元では、利用者がキャッシュを持ち、再取得を頼む呼び出しが別に要る。
- モニターをリソースに 1 つだけ張る。取得する内容が親（`cwd` など）で変わるなら、監視する対象も親で変わる。
- インスタンスに比較用の `key` を持たせ、プラグインが張り替えを判断する。張り替えの判断はモニターに任せるほうが、プラグインが単純になる。
- core が、利用者の関数を直接呼ぶ。ターミナルと流れが変わり、core が外部の状態に依存する。
- 子ターミナルを別のリソースにする。子ターミナルはターミナルそのもので、同じデータを別の形で通知し直すことになる。
